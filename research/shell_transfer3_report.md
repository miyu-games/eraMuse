## リプレイヤー実ログ適用（PC の実試遊ログ）

PC ビルド出力の実データ（`characters\base.json`／`logs\base.jsonl`／`trainers_state.json`、MD5 照合済みコピー）を隔離ホームへ移し、同梱エンジン（bun・`src/replay.ts`、PC 側 exe と同一ハッシュのビルド系統）で再生を1回実行した。**結果：完全再生できず（判定 ok=false、応答ミスマッチ73件／41レコード、最終状態不一致）。**

- 原因はリプレイヤーの欠陥ではなく、対象ログが「単一世代・新形式」という完全再生の前提を満たさないため：
  - ログは 2026-11-08 開始で、セッション再構築（1日2回制）**以前**の旧モデル（1日3行動・allowance 制）時代のレコードを含む。現行エンジンで旧モデル op を再生すると状態形そのものが合わない（`actionsLeft`/`actionsPerDay`/`allowance`/`dailyExp` 等の旧フィールド群が差分の中心）。
  - `start` レコードが11件＝複数世代のエンジン（再構築・忠実化・派生再構築）を跨いだ再開の積み重ね。旧エンジンの意味論で蓄積した値（juelSrcMark 等）は現行エンジンでは再現しない。
  - ログ形式拡張（2026-11-10）以前の開始のため start に `rngSeed`／`trainerStart` が無く、シードは元セーブから補完された（rngSeed 613789138、現セグメントの rngRolls は 2＝2 で一致）。ただし開始時点でトレーナーストアが素でなかった可能性は旧形式では判定不能。
- リプレイヤー機構そのものは新形式ログ（単一世代・119レコード）で完全一致を検証済み（`replayer_report.md`）。今回の実ログは、その検証範囲の外にある「世代跨ぎログ」であることが実測で確定した。
- なお再生はコピーに対してのみ実施し、PC 側の実セーブ・実ログには一切触れていない（照合で無傷を確認済み）。
- **含意**：試遊を新ビルドで新規開始すれば、そのログは次回から完全再生の対象になる。現在の base の進行（Day 2）を正本として残すなら JSON スナップショット側が正であり、ログ再生による復元はこのセーブには使えない。
